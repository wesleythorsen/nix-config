# Authorizer route-table gaps

Enumeration (phase 1) sometimes finds legacy routes the authorizer's route table cannot resolve. This playbook replaces "stop and report" with a consistent handling path. Observed on PLCR-4493 (agent): six explicit endpoints (`GET|POST /v1/agents`, `GET|PUT|DELETE /v1/agents/:agentId`, `GET /v1/catalog`) had no resolvable keys and shipped as a documented dependency.

## First: locate the live table and matcher — they move

- Route table: ts-service-gateway-api — was `scripts/route-policies.ts`, moved to `src/auth/rbac/route-policies.ts` in PLCR-4692; generated by `scripts/generate-route-policies.mjs`. Grep the repo for `route-policies` rather than trusting a path.
- Matcher: ts-lambda-core `lambdas/gatewayAuthorizer/src/routes/route-matcher.ts`. Check which branch actually carries it — as of PLCR-4041 the authorizer source lived only on the open PR branch (`PLCR-4041_upload_gw`), not on development.

## Classify the gap (matcher semantics decide everything)

Read the CURRENT matcher before classifying; the semantics below were verified against the PLCR-4041 matcher (`matchRoute`/`matchByPath`):

1. **Explicit resource, missing exact template key.** Explicit (non-proxy) resources resolve by parameterized-template lookup ONLY — `GET /v1/agents/:agentId` needs that exact key; greedy `/v1/agents/*` is never consulted. Gap type: needs exact keys.
2. **Bare prefix path.** The greedy walk never matches an empty suffix: `GET /v1/agents` does NOT hit `/v1/agents/*` (the walk also stops above top-level `/v1/*`). Bare paths need their own exact keys.
3. **Trailing `{proxy+}`, missing greedy key.** Concrete-path lookup tries exact key first, then `/a/b/*` before `/a/*`. If neither exists for the subtree, every request through the proxy denies.
4. **Non-trailing or multiple greedy segments.** Always denied by design — restructure the resources instead (see the variable-sibling constraint in cfn-authoring.md).

## Resolve or ship-with-dependency — 🛑 decision gate

Present both options with the gap classification:

**(a) Fix the table first** (separate work, two repos — get explicit go-ahead, it is outside this migration's diff):
1. Add the routes so the generator emits the missing keys: run `scripts/generate-route-policies.mjs` in ts-service-gateway-api and PR the regenerated table.
2. Rebuild/publish the gatewayAuthorizer bundle in ts-lambda-core (mind which branch owns the source).
3. Bump the pinned `LambdaMap.GatewayAuthorizer.S3Key` in ts-platform.yaml (coordinate merge order — the zip must exist before the pin lands).

**(b) Ship with a documented dependency** (the PLCR-4493 pattern):
- Open the dev PR as DRAFT with a prominent DO-NOT-MERGE note naming the exact missing keys and the unblock recipe (the three steps above).
- The predev3 leg still runs and verifies everything the table CAN resolve; list the denied endpoints explicitly in the verification comment.
- Record the dependency on the Jira ticket and do not mark the PR ready-for-review until the keys land.

Never silently drop the affected routes to make the PR "clean" — route parity is sacred; a dropped route is a regression at cutover, not a workaround.
