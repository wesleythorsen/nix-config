# Bucket-B pattern — large uploads via presigned URL

API Gateway REST APIs cap request payloads at 10 MB, so any legacy route that accepted a file body through the Hapi gateway cannot be proxied as-is. The platform's shipped answer is the presigned-URL flow from PLCR-4041 (fileinfo `/v1/datalake/upload*`, ts-lambda-core PR #3349, David Frenkel). Copy that pattern; don't invent a second one.

## The flow (as shipped for datalake uploads)

1. Client calls a small **upload-intent** endpoint through the new gateway (authorized like any other route). The upload Lambda validates the request and returns a **presigned S3 PUT URL** for an **intermediate bucket** plus the object key.
2. Client `PUT`s the bytes **directly to S3** — the gateway never sees the body.
3. S3 emits an object-created event → SQS/SNS (with retries and a DLQ) → a **validation Lambda** runs the same checks the legacy synchronous handler did (IDS schema / artifact validation, size, content type).
4. On success the object is copied to its final destination (data-lake or artifact bucket) and the existing downstream processing picks it up unchanged. On failure the object is quarantined and the client can poll status.

Agents still use the legacy synchronous upload endpoints and cannot switch yet — which is why the legacy gateway is not being decommissioned in 4.7. Treat agent-facing upload routes as out of scope for the new gateway unless the ticket says otherwise.

## What the skill produces for an upload route

The migration PR for the service **does not** proxy the upload route. Instead the skill:

1. **Enumerates** every upload-shaped route (see the detection signals in `migration-patterns.md`) and lists them under "Bucket B — large upload" at the phase-1 gate.
2. **Locates the reference implementation** in ts-lambda-core: the upload-intent Lambda, the validation Lambda, the intermediate-bucket CFN, and the S3→SQS wiring. Read the current code on the branch that carries it (as of PLCR-4041 that was the PR #3349 branch, not `development` — check).
3. **Writes a change plan** in the draft PR body and the ticket, per route:
   - client change: replace the direct body POST with intent → presigned PUT → (optional) status poll;
   - service change: an intent endpoint (or reuse the shared upload Lambda with a new `resourceType`), a validation handler for this service's content type, and the destination-bucket copy;
   - infra: intermediate bucket/prefix, event wiring, DLQ, IAM for the two Lambdas — copied from the datalake stack;
   - gateway: the intent endpoint and status endpoint ride the new gateway as normal bucket-A routes with CORS.
4. **Drafts the service-side PR** in the owning repo when the requester asks for it (🛑 gate — it's a second repo and a behavior change), following the reference as closely as the service allows. Otherwise the plan alone is the deliverable and the route is recorded as a documented dependency (same hygiene as `authorizer-gaps.md`: DRAFT PR, DO-NOT-MERGE note naming the route, ticket comment).
5. **Verification** (`verification-tests.md`): intent endpoint answers through the gateway; a presigned PUT of a small fixture lands in the intermediate bucket; the validation Lambda logs a pass; the object appears at the final destination. Run against predev3 with a non-admin token.

## Things that have bitten before

- The presigned URL must be generated by a role that can `PutObject` on the intermediate bucket **and** the client must send the exact `Content-Type` the URL was signed for — mismatches are a 403 from S3, not from us.
- Keep the intermediate bucket prefix per service (`<service>/<orgSlug>/…`) so the validation Lambda can route by prefix.
- CORS on S3 is separate from CORS on the gateway: the intermediate bucket needs a CORS rule allowing the UI origin's `PUT`.
- Never mark the legacy upload route as removed in the gateway diff — agents still hit it. Parity rule applies: the legacy gateway keeps serving it.
